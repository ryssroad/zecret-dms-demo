# Envelope v0

Редакция 3.1. Codec реализован в этой демонстрационной копии. Это рабочая спецификация исследовательского прототипа, не заключение независимого человеческого аудита.

Связанные спецификации: [envelope](envelope-v0.md), [policy/setup](policy-v1.md), [session](session-v0.md). Описания ролей и сетевого поведения задают требования будущей интеграции и не означают, что эти компоненты реализованы.

## Итог

- **Конверт одного размера.** Каждая запись дополняется нулями до 344 байт открытого текста и запечатывается в конверт ровно из 384 байт: nonce (24), шифротекст (344), тег (16). Двоичное memo — `0xFF` и эти 384 байта, текстовое — Base64 от них, ровно 512 символов. Самая длинная запись (ROTATE, RECOVER) — 275 байт из 344.
- **Поле `generation`.** Поколение операционной линии задаёт RECOVER. Эквивокация считается только внутри текущего поколения: так старый ключ после восстановления не возвращает сессию в компрометацию.
- **Два шага.** Разбор конверта не зависит от состояния сессии: расшифровка, структура, ключи из `body`. Подпись проверяется потом, в state machine, набором ключей нужного поколения и эпохи.

## Обозначения

- Целые — big-endian, фиксированной ширины. `‖` — конкатенация.
- `H_p(x)` — BLAKE2b с параметром `hash_length = 32` (не усечение BLAKE2b-512), без ключа и соли, `fanout = 1`, `depth = 1`, персонализация `p` — 16 ASCII-байт.

| Хеш | Персонализация | Что хеширует |
| --- | --- | --- |
| `H_sess` | `zecret-v1-sessid` | `session_secret` → идентификатор сессии |
| `H_rec` | `zecret-v1-record` | байты записи (с подписью, без дополнения) → `rid`, `prev` |
| `H_pol` | `zecret-v1-policy` | байты PolicyV1 → поле `policy` |
| `H_ct` | `zecret-v1-cipher` | зашифрованный пакет C → `payload_hash` политики |
| `H_setup` | `zecret-v1-setup_` | байты SetupV1 → `setup_id` |

## Запись (record)

| Смещение | Длина | Поле | Значение |
| --- | --- | --- | --- |
| 0 | 1 | `version` | `0x01` = zecret/v1 |
| 1 | 1 | `network` | `0x00` mainnet, `0x01` testnet, `0x02` regtest |
| 2 | 1 | `type` | см. таблицу типов |
| 3 | 32 | `session` | `H_sess(session_secret)` |
| 35 | 4 | `generation` | u32: у операционных записей — поколение; у RECOVER — открываемое поколение; у CANCEL — 0 |
| 39 | 8 | `epoch` | u64: у операционных — номер в поколении; у административных — административный номер; `u64::MAX` отклоняется |
| 47 | 4 | `issued_height` | u32, вершина цепочки, которую видел владелец при подписи |
| 51 | 32 | `prev` | предыдущая запись своей линии (правила — в session-v0) или 32 нулевых байта |
| 83 | 32 | `policy` | `H_pol` исходной политики сессии (в v0.1 политика неизменяема) |
| 115 | 32 | `head` | v0.1: 32 нулевых байта, иначе отказ; ненулевое значение потребует новой `version` |
| 147 | N | `body` | зависит от `type` |
| 147+N | 64 | `sig` | Ed25519 |

| `type` | Код | Линия | N | `body` |
| --- | --- | --- | --- | --- |
| HEARTBEAT | `0x01` | операционная | 0 | — |
| PANIC | `0x02` | операционная | 0 | — |
| ROTATE | `0x03` | операционная | 64 | новый основной ключ (32) ‖ новый duress-ключ (32) |
| CANCEL | `0x04` | административная | 0 | — |
| RECOVER | `0x05` | административная | 64 | новый основной ключ (32) ‖ новый duress-ключ (32) |
| EXTEND | `0x06` | — | — | зарезервирован: отказ при разборе |
| прочие | — | — | — | отказ при разборе |

Длины: HEARTBEAT, PANIC, CANCEL — 211 байт; ROTATE, RECOVER — 275.

## Подпись и идентичность

- Подписываемое сообщение: `"zecret/v1" ‖ 0x00 ‖ record[0 .. 147+N]` — все поля, кроме `sig`. Сеть и сессия входят как поля записи, строка `zecret/v1` — доменный префикс.
- `rid = H_rec(record)` по байтам записи вместе с `sig`, без дополнения.
- Шифрование и транспорт в `rid` не входят. Та же запись, заново зашифрованная или в другом режиме, — то же событие. Дедупликация везде идёт по `rid`, а не по memo или txid.
- Поля «каким ключом подписано» нет. Тот, у кого нет `SessionEnvelopeKey` и публичных ключей сессии, не отличит duress-запись от обычной. Guardian их различает намеренно.

## Профиль Ed25519

Нормативны сами проверки. Ссылки на ed25519-dalek 2.x даны как пример реализации.

- **Публичный ключ** принимается, если:
  1. 32 байта декодируются как точка кривой (`VerifyingKey::from_bytes`);
  2. каноническое кодирование этой точки совпадает со входом. Каноничность проверяется нормализацией самой точки, например `key.to_edwards().compress().to_bytes()`. `VerifyingKey::to_bytes()` для этого не подходит: он возвращает сохранённые входные байты;
  3. точка не малого порядка (`is_weak() = false`).
- **Набор ключей сессии** — текущие основной и duress плюс ключ восстановления — попарно различен по байтам. Проверяется при setup и при каждой ROTATE и RECOVER.
- **Отказ по ключам** отвергает запись или setup целиком: текущие ключи не меняются частично.
- **Подпись** `(R, S)` для публичного ключа `A` и сообщения `M` действительна, только если одновременно:
  1. `A` проходит проверку публичного ключа (выше);
  2. 32 байта `R` канонически кодируют точку кривой не малого порядка;
  3. `S`, прочитанное как little-endian целое, меньше порядка группы `ℓ = 2^252 + 27742317777372353535851937790883648493`;
  4. выполняется уравнение без кофактора `[S]B = R + [k]A`, где `k = SHA-512(R ‖ A ‖ M) mod ℓ`, `B` — базовая точка (RFC 8032, раздел 5.1.7).

  Этому соответствует `VerifyingKey::verify_strict` в ed25519-dalek 2.x. Отрицательные векторы — неканоничный `R`, `R` малого порядка, `S ≥ ℓ`, неверное уравнение — находятся в `docs/test-vectors/`.
- **Классификация подписи.** Подпись проверяется каждым ключом набора, выбранного по правилам session-v0. Ровно одно совпадение даёт `Main`, `Duress` или `Recovery`. Ноль совпадений — подпись недействительна. Больше одного — запись отвергается как неоднозначная (при попарно различных ключах для корректной подписи это недостижимо).

## Шифрование

- `plaintext = record ‖ 0x00 × (344 − len(record))`, всегда 344 байта. Ненулевой байт после конца записи (длина по `type`) — отказ.
- AEAD: XChaCha20-Poly1305. Ключ — `SessionEnvelopeKey` (32 байта). Nonce — 24 случайных байта из системного криптографического генератора.
- AAD: `ASCII("zecret/v1") ‖ u8(network)`, ровно 10 байт. `network` берётся из доверенной конфигурации guardian'а, а не из данных memo.
- `sealed = nonce ‖ ciphertext(344) ‖ tag(16)`, всегда 384 байта.

## Представление в memo

| Режим | 512 байт memo | Создаёт в v0.1 | Разбирает guardian |
| --- | --- | --- | --- |
| Двоичный | `0xFF` ‖ `sealed` ‖ `0x00` × 127 | owner | да |
| Текстовый | Base64 (RFC 4648, стандартный алфавит, без `=` и пробелов) от `sealed` — ровно 512 ASCII-символов | никто | да |

Хвост двоичного memo отправитель заполняет нулями, получатель его не проверяет: он не подписан и на `rid` не влияет. Одна запись в обоих режимах даёт один `rid`.

## Разбор (шаг 1)

Вход — ровно 512 байт memo и доверенная конфигурация: сеть и набор сессий с их `SessionEnvelopeKey` и `H_pol`. От состояния сессий разбор не зависит.

1. **Конверт.** `memo[0] = 0xFF` → `sealed = memo[1..385]`. Иначе, если все 512 байт — символы алфавита Base64, `sealed` — их декодирование. Иначе это не envelope.
2. **Расшифровка** ключом каждой сессии guardian'а с AAD своей сети. Не открылось ни одним — не envelope этого guardian'а.
3. **Структура.** Проверяются: `version = 0x01`; `network` — своя сеть; `type` известный и не зарезервированный; `epoch ≠ u64::MAX`; `head` нулевой; дополнение нулевое; у CANCEL `generation = 0`; у ROTATE и RECOVER ключи из `body` проходят проверку публичного ключа по профилю.
4. **Сессия.** `session` совпадает с сессией, чьим ключом открылся конверт, а `policy` — с `H_pol` её политики.

Результат — разобранная запись: байты, `rid`, подписываемое сообщение, подпись, сессия. Подпись на этом шаге не проверяется: набор ключей зависит от истории сессии (session-v0, «Приём записи» и «Эквивокация»).

Отказ разбора означает, что memo получено и прочитано достоверно, но это не наша запись. Оно пропускается без паники и без изменения состояния, в счётчик отброшенного. Сетевой сбой, невозможность получить транзакцию или ошибка хранилища — **не** отказ разбора: они останавливают продвижение обработанной высоты.

| --- | --- |
| Лимит memo | 512 |
| Полезная часть двоичного memo | 511 |
| Конверт `sealed` | 384 |
| Открытый текст (с дополнением) | 344 |

Тесты фиксируют: `len(Base64(sealed)) = 512`, `len(record) ≤ 344` для каждого типа, один `rid` у записи в обоих режимах.

## Допущения прототипа

- Перебор ключей всех сессий guardian'а на каждое memo стоит O(число сессий). Для прототипа это приемлемо. Лимиты очереди guardian'а не должны приводить к пропуску данных с последующим выводом «heartbeat не было».
- Одинаковая длина конверта скрывает тип записи от relay, но не сетевую активность целиком: время и факт отправки relay видит.
